NODE.JS AUTHENTICATION TOOLKIT

Complex authentication.
Simple methods. Full control.

Security building blocks for Node.js apps, with your database, controllers, and business rules still in your hands.

Start building →View on GitHub ↗
TypeScriptESMNode.js 22+Express 4 & 5
THE PROBLEM

Keep the security mechanics. Keep ownership of your app.

Authentication has sharp edges: password truncation, token validation, rotation races, stale role claims, and error leaks. Full frameworks can also make choices about users, persistence, and application flows that do not fit every backend.

RST-Auth packages reusable mechanics and leaves application-specific work with you. It does not create users, issue database queries, define roles, or dictate API responses.

01

Security primitives

bcryptjs password hashing, jose access tokens, and opaque rotating refresh tokens.

02

Small adapters

Optional Express 4/5 and Zod integrations around a framework-independent core.

03

Your architecture

Inject configuration and implement your repositories and persistent token store.

01 · INSTALL

Add RST-Auth to a Node.js project

Requires Node.js 22 or newer. The core package uses ESM; Express and Zod are optional peers.

Terminal 
npm install rst-auth
npm install express zod
npm install --save-dev @types/express

Install only the peers your app uses. The core entry does not load Express or Zod.

02 · QUICK START

Create the auth services

Read secrets in your app's config layer and inject them. The library never reads process.env.

src/auth.ts 
import { createAuth } from "rst-auth";

const secret = process.env.ACCESS_TOKEN_SECRET;
if (!secret || Buffer.byteLength(secret, "utf8") < 32) {
  throw new Error("ACCESS_TOKEN_SECRET must be at least 32 bytes");
}

export const auth = createAuth({
  accessToken: {
    key: new TextEncoder().encode(secret),
    issuer: "my-service",
    audience: "my-api",
  },
});
Production: set mode to production, provide issuer and audience, use a strong key, and keep access tokens short-lived.
CONFIGURATION REFERENCE

Settings are validated when the service is created

password.workFactorDefault 12; integer from 4 through 31. Higher costs use more CPU.
accessToken.keyRequired. HMAC keys need at least 32 bytes; asymmetric keys are supported.
algorithm / algorithmsHS256 by default. Verification algorithms are explicitly allowlisted.
issuer / audienceOptional in development; required with production mode.
expiresInSecondsAccess token lifetime defaults to 900 seconds; production caps it at one hour.
refreshTokenTtl / absoluteLifetimeBoth required when refresh is configured; rotation respects the family lifetime cap.

Configuration is injected as a JavaScript object. The library does not read environment variables. See the full configuration guide.

optional subpaths 
rst-auth           core services and types
rst-auth/express  Express middleware and cookie helpers
rst-auth/zod      Zod validation adapter
rst-auth/testing  refresh-store conformance suite
03 · PASSWORDS

Hash passwords before storing them

Store only the hash. Compare passwords through the service during login, and do a dummy comparison when an account is absent.

signup and login 
const passwordHash = await auth.password.hash(password);
await users.create({ email, passwordHash });

const user = await users.findByEmail(email);
if (!user) {
  await auth.password.verifyDummy(password);
  throw new AuthError("UNAUTHORIZED", "Invalid email or password");
}
if (!(await auth.password.verify(password, user.passwordHash))) {
  throw new AuthError("UNAUTHORIZED", "Invalid email or password");
}
  • Passwords over 72 UTF-8 bytes are rejected because bcrypt truncates longer inputs.
  • The default work factor is 12. Benchmark on deployment hardware.
  • Dummy verification reduces account-enumeration timing differences; it does not guarantee identical response times.
04 · ACCESS TOKENS

Sign and verify access tokens

Tokens use jose. The configured algorithm allowlist stays pinned; a token header never selects the verification algorithm.

session controller 
const accessToken = await auth.tokens.generateAccessToken({
  sub: user.id,
  role: user.role,
});

const claims = await auth.tokens.verifyAccessToken(accessToken);
// Signature, expiry, configured issuer/audience,
// required claims, and access-token type are verified.

JWT claims are visible to their holder. Do not put secrets in them. Roles can become stale; use identity lookup or revocation checks when the app needs current account state.

05 · REFRESH TOKENS

Rotate refresh tokens with server-side state

Refresh tokens are opaque random values. The store keeps SHA-256 hashes, not raw tokens. Rotation consumes the old token and creates a successor in the same family.

auth.ts 
import { createAuth, MemoryRefreshTokenStore } from "rst-auth";

const auth = createAuth({
  accessToken: { key },
  refreshToken: {
    store: new MemoryRefreshTokenStore(), // local demo only
    refreshTokenTtl: 60 * 60 * 24 * 7,
    absoluteLifetime: 60 * 60 * 24 * 30,
  },
});

const pair = await auth.refresh!.issue({ subject: user.id });
const rotated = await auth.refresh!.rotate(pair.refreshToken);
Production requirement: implement a persistent shared RefreshTokenStore with atomic consume. The built-in memory store loses state on restart and is unsafe across instances.

Reusing a consumed token revokes its entire family. Unknown, expired, revoked, and reused tokens never produce a new pair. Rotation cannot extend a family past its absolute lifetime.

06 · EXPRESS

Protect routes; keep your controllers

The adapter supports Express 4 and 5, parses Bearer headers strictly, and puts verified claims on req.auth.

routes.ts 
import { expressAuth } from "rst-auth/express";

const middleware = expressAuth(auth);
app.get("/me", middleware.authenticate(), getProfile);
app.get(
  "/admin",
  middleware.authenticate(),
  middleware.authorize({ roles: ["admin"] }),
  getAdminDashboard,
);
app.use(middleware.errorHandler());

No role data means deny. Missing or invalid auth returns 401; an authenticated user without a required role receives 403. Optional auth uses authenticate({ required: false }).

07 · VALIDATION

Keep parsed input explicit

routes.ts 
import { z } from "zod";
import { zodAdapter } from "rst-auth/zod";

const middleware = expressAuth(auth, { validator: zodAdapter() });
const itemSchema = z.object({ name: z.string().min(1) });
app.post("/items", middleware.validate({ body: itemSchema }), createItem);

Parsed values go to req.validated; request body, params, and query are not silently replaced. Core validation uses an adapter, so Zod is optional.

08 · ERRORS

Stable codes. Safe client responses.

AuthError includes a code, developer message, safe public message, status, and optional cause. Express emits safe fields by default.

custom formatter 
const middleware = expressAuth(auth, {
  errorFormatter: (error) => ({
    status: error.status,
    body: { error: { code: error.code, message: error.message } },
  }),
});

Never return passwords, hashes, secrets, tokens, stack traces, or raw internal errors to clients.

TOKEN DELIVERY

Choose how your app delivers tokens

For an API client, return the access token and send it as an Authorization Bearer header. Keep refresh tokens out of URLs. For browser apps, the Express adapter can set an HttpOnly, Secure, SameSite cookie.

cookie helpers 
import {
  setRefreshTokenCookie,
  fromCookie,
} from "rst-auth/express";

setRefreshTokenCookie(res, refreshToken); // HttpOnly, Secure, SameSite=Lax
const token = await fromCookie("refreshToken")(req);
Trade-off: cookies reduce direct JavaScript access to refresh tokens, but browsers attach them automatically, so your app needs CSRF protection and a deliberate SameSite/origin policy. Bearer tokens require explicit attachment; protect browser storage against XSS.

Read the cookie vs Bearer guide.

09 · END-TO-END

Your app owns account creation

The example's repository owns uniqueness, role assignment, and storage. Signup rejects unknown fields such as client-supplied role.

signup controller 
async function signup(req, res) {
  const { email, password } = req.validated.body;
  const passwordHash = await auth.password.hash(password);
  const user = await users.create({ email, passwordHash, role: "user" });
  const accessToken = await auth.tokens.generateAccessToken({
    sub: user.id,
    role: user.role,
  });
  const refresh = await auth.refresh.issue({ subject: user.id });
  res.status(201).json({ user: { id: user.id }, accessToken,
    refreshToken: refresh.refreshToken });
}
Never trust a role from signup input. Reject or ignore privilege fields; assign roles using server-owned policy.

Run the Express API example to try signup, login, protected routes, refresh replay detection, and logout using the packed package.

10 · SECURITY BOUNDARIES

What your application still handles

Configure controls that fit your app and deployment.

CORSChoose trusted browser origins and credential policy.
Rate limitingProtect signup, login, and recovery endpoints.
CSRFCookie-based refresh needs an anti-CSRF strategy.
Account lifecycleBuild lockout, password reset, and email verification.
Authorization freshnessCheck current permissions when token roles may be stale.
OperationsStore secrets safely and persist refresh state atomically.
11 · LIMITATIONS

Know what this package does not provide

  • Alpha software; APIs and policies may change before a stable release.
  • No production database, user model, or persistent refresh store is bundled.
  • No hosted identity provider, OAuth, MFA, passkeys, email verification, password reset, lockout, or rate limiter.
  • Access tokens are stateless unless a revocation hook is configured; deleting a user alone does not invalidate issued tokens.
  • MemoryRefreshTokenStore is process-local and only for tests and local examples.
  • Tests are not a security audit and cannot prove every distributed-store failure mode.
12 · TESTING

Check your refresh store contract

Consume must be atomic across concurrent requests and app instances. Register the framework-agnostic conformance suite:

store.test.ts 
import { registerRefreshTokenStoreConformanceTests } from "rst-auth/testing";

registerRefreshTokenStoreConformanceTests(
  { test: (name, fn) => it(name, fn) },
  () => createFreshDatabaseStore(),
);

The suite checks rotation, replay, family revocation, expiry, revocation, and one-winner concurrent consume. It does not replace review of the database's transaction and consistency guarantees.

13 · COMMUNITY

Contribute to RST-Auth

Contributions are welcome, from a documentation fix to a security improvement. Start with an issue for larger changes so the scope and expected behavior are clear before you invest time.

03 · KEEP SCOPE

Preserve app ownership

User records, database queries, roles, routes, and business rules belong to the application. Never trust a client-supplied role during signup.

local checks 
npm ci
npm run build
npm test
npm run lint
npm run typecheck
npm run format:check

Before opening a pull request

  • Add or update focused tests for behavior changes. Security claims in the docs should map to tests in docs/claims.md.
  • Update the documentation when public behavior or configuration changes; keep examples consistent with the package API.
  • Describe the motivation, implementation, tests, security impact, and compatibility impact in the pull request.
  • Follow the project Code of Conduct. Do not include real secrets, tokens, or personal data in commits or issue reports.
